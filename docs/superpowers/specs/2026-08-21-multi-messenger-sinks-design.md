# Мультімесенджерні сінки: універсальний контракт адаптера

**Дата:** 2026-08-21
**Статус:** затверджено до планування
**Скоуп:** заміна зашитого Telegram-виводу на таблицю сінків (Telegram, Discord, Slack, generic webhook)

## 1. Проблема

Пайплайн `fetch → parse → state → format → send` жорстко привʼязаний до Telegram:

- `aggregator/format.py` рендерить Telegram-HTML і нічого іншого не вміє;
- `aggregator/telegram.py` знає про `api.telegram.org`, `parse_mode`, `parameters.retry_after`;
- `aggregator/main.py` читає `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` з оточення;
- `state.json` тримає один плоский список `seen`, тобто поняття «кому вже надіслано» не існує.

Треба публікувати ті самі статті ще й у Discord, Slack і довільний webhook, з різними наборами фідів на різні цілі.

## 2. Рішення (огляд)

Вводимо **сінк** — пару «рендер + транспорт» для одного типу месенджера, заданих рядком у таблиці `SPECS`. Ядро (`fetch`/`parse`/`state`/`main`) про месенджери не знає нічого: воно викликає `sinks.send(article, target, client)`.

Розглянуті й відхилені альтернативи:

- **Пакет `sinks/` з модулем на месенджер + реєстр `BUILDERS`.** Відхилено після заміру: різниця між Discord, Slack і generic webhook — це пʼять скалярів (маркер жирного, екранувальник, ключ payload, ліміт, звідки читати затримку 429). Пʼять скалярів — це рядок таблиці, а не модуль. Чотири модулі означали б чотири копії одного блоку імпортів, `build()` і збірки payload (~200 рядків проти ~115). Якщо колись зʼявиться месенджер, який справді не вкладається в таблицю, підвищити рядок до окремої функції — механічна робота на двадцять хвилин.
- **Шаблони payload у YAML** (нових месенджерів без коду). Відхилено: Telegram усе одно випадає з generic-моделі, помилки шаблону ловляться лише в рантаймі, а конфіг перетворюється на міні-мову. Складність переїжджає, а не зникає.
- **Дві незалежні осі — рендерери × транспорти.** Відхилено: N×M комбінацій і зайвий рівень непрямості на чотири цілі.

## 3. Конфігурація

Новий файл `targets.yaml` поруч із `feeds.yaml`:

```yaml
targets:
  - name: tg-main            # довільний ідентифікатор, ключ у state.json
    type: telegram
    token: ${TELEGRAM_BOT_TOKEN}
    chat_id: ${TELEGRAM_CHAT_ID}
    tz: Europe/Kyiv          # необовʼязково, дефолт — значення --tz

  - name: discord-ai
    type: discord
    url: ${DISCORD_WEBHOOK_URL}
    tiers: [1, 2]

  - name: slack-team
    type: slack
    url: ${SLACK_WEBHOOK_URL}
    tags: [openai, deepmind]

  - name: n8n
    type: webhook
    url: ${N8N_WEBHOOK_URL}
    exclude_tags: [tds]
```

Правила:

- `name` і `type` обовʼязкові; `name` унікальний у межах файлу.
- Обовʼязкові поля за типом: `telegram` — `token` і `chat_id`; решта типів — `url`.
- **Невідомі ключі відхиляються.** Друкарська помилка `chat_ids:` має падати в лоадері, а не за пів року тиші. Дозволені ключі: `name`, `type`, `url`, `token`, `chat_id`, `tz`, `tiers`, `tags`, `exclude_tags`.
- Значення виду `${VAR}` резолвиться з оточення при завантаженні. Резолв застосовується лише коли значення **цілком** дорівнює `${VAR}`; інтерполяція всередині рядка не підтримується. Літеральні значення дозволені (зручно локально), але секрети в репозиторій не кладемо: webhook-URL Discord і Slack самі по собі є секретами.
- Повідомлення про помилку називає ціль і **імʼя змінної**, ніколи не її значення.
- `tz` перетворюється на `ZoneInfo` **у лоадері**. Друкарська помилка `Europe/Kiyv` має падати одразу, а не кидати `ZoneInfoNotFoundError` з середини рендеру при кожній відправці (див. §8).
- `tiers`, `tags`, `exclude_tags` — необовʼязкові фільтри, спільні для всіх типів.

### 3.1 Дві категорії помилок конфігу

Розрізнення важливе, бо від нього залежить, чи піде розсилка взагалі (§8):

| категорія | приклади | реакція |
|---|---|---|
| **Малформований конфіг** — помилка людини, виправляється в репо | невідомий `type`, дубль `name`, відсутнє обовʼязкове поле, невідомий ключ, невалідна `tz` | `ValueError` у `load_targets`, до фетчу фідів. Не шлемо нічого. |
| **Нерезолвлений `${VAR}`** — операційна проблема, конфіг валідний | секрет ротували, Slack-застосунок видалили, змінна не задана в CI | ціль пропускається з `ERROR`, **решта цілей працює**, процес виходить із кодом 1. |

Друга категорія — пряме наслідування того, що цілі незалежні за побудовою. Якщо видалений `SLACK_WEBHOOK_URL` глушить Telegram, який працював до появи цього проєкту, ізоляція помилок нічого не варта.

## 4. Моделі

`aggregator/models.py` (поруч із наявним `FeedSource`):

```python
@dataclass(frozen=True)
class Target:
    name: str
    type: str
    tz: ZoneInfo
    url: str = ""
    token: str = ""
    chat_id: str = ""
    tiers: tuple[int, ...] = ()
    tags: tuple[str, ...] = ()
    exclude_tags: tuple[str, ...] = ()

    def matches(self, article: Article) -> bool:
        """tiers ∧ tags ∧ ¬exclude_tags; порожній фільтр не фільтрує."""
```

Поля пласкі, без словника `options`. Словник коштував би валідації замість того, щоб її економити: кожен тип мусив би сам перевіряти наявність своїх ключів, а `chat_ids:` проліз би до рантайму.

`Article` отримує поле `tier: int` — фільтрація по tier відбувається на рівні статті, а `parse_feed` уже має `FeedSource` під рукою. `FeedSource` без змін.

## 5. Сінки

Один модуль `aggregator/sinks.py`, що замінює `format.py` і `telegram.py` (тобто в проєкті стає на один файл менше).

### 5.1 Таблиця

```python
class Spec(NamedTuple):
    esc_text:  Callable[[str], str] | None
    esc_url:   Callable[[str], str] | None
    bold:      tuple[str, str]
    limit:     int
    key:       str                        # ключ payload, у який кладеться текст
    delay:     float                      # пауза між відправками
    retry_after: Callable[[Response], Any]

SPECS = {
    "telegram": Spec(html.escape, html.escape, ("<b>", "</b>"), 4096, "text", 3.5,
                     lambda r: r.json()["parameters"]["retry_after"]),
    "discord":  Spec(_md_escape,  None,        ("**", "**"),    2000, "content", 2.0,
                     lambda r: r.json()["retry_after"]),
    "slack":    Spec(_slack_escape, _slack_escape, ("*", "*"),  4000, "text", 1.2,
                     lambda r: r.headers["Retry-After"]),
    "webhook":  Spec(None, None, ("", ""), 0, "", 0.0,
                     lambda r: r.headers["Retry-After"]),
}
```

Для `webhook` поля `esc_*`, `bold`, `limit` і `key` не застосовуються — цей тип не рендерить текст (§5.3); нулі та порожні рядки стоять як заглушки, а гілка `webhook` до них не звертається.

Значення в таблиці іменовані (`NamedTuple`), бо `SPECS[t.type][5]` нечитабельне. Це таблиця констант, а не обʼєкт на ціль.

**Затримки виведені з реальних лімітів:** Telegram ≈20 повідомлень/хв у чат → `3.5` (≈17/хв). Discord — ліміт **каналу** 30 повідомлень/хв → `2.0`; `1.0` дав би 60/хв і ціль проводила б більшість часу в ретраях. Slack incoming webhook — 1 повідомлення/с на webhook → `1.2`, бо сидіти рівно на межі означає ловити 429.

**Екранування — окреме для тексту й URL, і це не косметика.**
`_slack_escape` перетворює `&`, `<`, `>` — саме це не дає заголовку `<!channel>` з RSS підняти весь воркспейс.
`_md_escape` бекслешить `` \ ` * _ ~ | > [ ] ( ) `` — без цього заголовок `[Free iPhone](https://evil.example)` рендериться в Discord як клікабельне посилання з підміненим текстом.
URL для Discord **не екранується**: бекслеші перед `_` і `(` ламають автолінк, і посилання виду `.../Foo_(bar)` мертве.

### 5.2 Публічний інтерфейс

```python
def payload(article: Article, target: Target) -> dict     # що йде на дріт
def preview(article: Article, target: Target) -> str      # текст для --dry-run
def send(article: Article, target: Target, client, *, sleep=time.sleep) -> None

class PermanentSendError(Exception): ...
```

`preview` існує, бо `--dry-run` (§9) мусить показати те саме, що пішло б у мережу, і при цьому нічого не слати. Для текстових типів це `payload(...)[spec.key]`, для `webhook` — `json.dumps` усього payload.

### 5.3 Текст повідомлення

Скелет спільний для трьох текстових типів, різниться лише маркер жирного й екранування:

```
🔹 {B}{title}{/B}
{source} · {HH:MM, DD Mon}
                          ← порожній рядок і summary лише якщо summary непорожній
{summary}

{url}
#{tag}
```

Без `published` замість часу стоїть `—`. Час форматується у `target.tz`. Це рівно нинішній `format.py`, узагальнений по маркеру жирного — Telegram-вивід не змінюється ні на символ.

`webhook` не рендерить текст. Його payload походить від дата-класу, а не переписується вручну:

```python
{**asdict(article), "published": article.published.isoformat() if article.published else None}
```

Перелічувати вісім ключів руками означає, що payload протухне при наступному полі в `Article` — а це відбувається просто зараз, разом із `tier`.

### 5.4 Payload по типах

| тип | URL | payload |
|---|---|---|
| telegram | `https://api.telegram.org/bot{token}/sendMessage` | `{chat_id, text, parse_mode: "HTML"}` |
| discord | `target.url` | `{"content": text, "allowed_mentions": {"parse": []}}` |
| slack | `target.url` | `{"text": text}` |
| webhook | `target.url` | див. §5.3 |

`allowed_mentions` обовʼязковий: без нього стаття із `@everyone` у заголовку пінгає весь сервер із webhook, який оператор не може «відкликати». Slack від цього захищений екрануванням `<` і `>`.

Ключ `disable_web_page_preview` прибираємо: він deprecated з Bot API 7.0, а `false` там і так дефолт.

### 5.5 Ліміти й обрізання

`parse.clean_summary` уже ріже summary до `SUMMARY_LIMIT = 300`, тож реальне повідомлення — ~600 символів і в жоден ліміт не впирається. Ліміти в таблиці — страховка від патологічно довгого заголовка, не гаряча гілка.

Обрізаємо **summary до рендеру**, ніколи не готовий текст. Різати зрендерений рядок можна посеред HTML-сутності (`&am`) або перед `</b>`, і Telegram відповість 400 — тобто постійною помилкою (§8). Якщо навіть з порожнім summary текст не влазить, обрізається заголовок.

### 5.6 Ретраї на 429

Одна функція всередині `send`, спільна для всіх типів:

- на `429` читаємо затримку через `spec.retry_after`;
- **екстрактор викликається в `try/except Exception: 1.0`.** Discord за Cloudflare віддає на 429 HTML, і `resp.json()` кидає `JSONDecodeError`; заголовок `Retry-After` легально буває HTTP-датою, і `float()` кидає. Без цього guard'а ретраєбельний 429 перетворюється на жорсткий фейл. **Це живий баг у `aggregator/telegram.py:27` уже зараз.**
- затримка клемпиться: `min(value, 60.0)`. Заголовок `Retry-After: 86400` інакше припаркує раннер GitHub Actions на добу.
- після `max_retries = 3` невдалих спроб — `RuntimeError` (транзієнтна помилка, див. §8).

## 6. Стан

```json
{"targets": {"tg-main": ["id1", "id2"], "discord-ai": ["id1"]}}
```

```python
load_state(path) -> dict[str, list[str]]        # внутрішній мапінг; {} якщо файлу немає
save_state(path, seen_by_target) -> None        # пише {"targets": ...}
select_new(articles, seen_ids) -> list          # без змін
```

`MAX_IDS` стає капом **на ціль** і зменшується 2000 → **500**. Кап на ціль — не церемонія: спільний кап дозволив би активній цілі витіснити id тихої цілі й спричинити тихі повторні пости. Число зменшено, бо `state.json` комітиться назад у репо двічі на добу: чотири цілі × 2000 id ≈ пів мегабайта, що переписуються назавжди в історії репозиторію розміром ~20 КБ. Дедуплікація має пережити лише вікно RSS (~700 id в обігу на 14 фідів), тож 500 на ціль покриває ~10 днів.

**Міграції немає — це свідоме рішення, а не відсутність даних.** Агрегатор працює в продакшені з 9 липня 2026: на `origin/main` лежить живий `state.json` у старому плоскому форматі `{"seen": [...]}` з 2000 id (~115 КБ), оновлюваний двічі на добу.

Мігрувати його ми не будемо. Ціною одного пропущеного 12-годинного вікна новин Telegram проходить тим самим seed-шляхом, що й будь-яка нова ціль (нижче), і ми не пишемо ~10 рядків `migrate_state` плюс тести, які виконаються рівно один раз за життя проєкту. Після першого запуску нового коду ключ `seen` зникає з файлу, бо `save_state` перезаписує документ цілком.

Наслідок, який треба прийняти явно: **перший прод-запуск після мерджу нічого не опублікує** — він засідить Telegram поточними статтями. Це очікувана поведінка, а не збій.

`MAX_IDS` = 500 при цьому не «обрізає» живі дані: старі 2000 id не переносяться взагалі, новий seed починається з ~700 id у RSS-вікні.

**Перший запуск — per-target.** Ціль, відсутня в стані, seed-иться поточними відібраними статтями й не постить нічого. Це автоматично покриває додавання нової цілі через півроку: вона не вивалює бекафіг, а починає з наступного запуску. Окремого коду під це не потрібно — той самий шлях, що й перший запуск усього проєкту.

**Перейменування цілі** = нова ціль: вона seed-иться, старий ключ лишається в `state.json` сиротою. Задокументувати в README; коду під це не пишемо.

**Формат стану односторонній, і це реальний ризик, а не теоретичний.** Прод працює, тож після мерджу `state.json` у репо буде в новому форматі. Старий код на ньому: `state.get("seen", [])` повертає `[]`, а не `None`, тобто first-run guard не спрацьовує, `select_new` бачить порожній seen — і в канал летить увесь бекафіг з 14 фідів. Відкат коду вимагає **спочатку** видалити `state.json`. Виносимо це в README окремим застереженням.

## 7. Потік у `main.run()`

```
targets, skipped = load_targets(targets_path, default_tz)   # малформований конфіг → виняток тут
articles = collect_articles(feeds, client)                  # один раз на всі цілі
state = load_state(state_path)
failed = list(skipped)

for target in targets:
    matched = [a for a in articles if target.matches(a)]

    if target.name not in state and not dry_run:
        state[target.name] = [a.id for a in matched]        # seed, нічого не шлемо
        save_state(state_path, state)
        continue

    queue = sorted(select_new(matched, state.get(target.name, [])),
                   key=lambda a: a.published or EPOCH)
    if len(queue) > MAX_SENDS_PER_RUN:
        log.info("target %s: %d queued, sending %d, rest next run",
                 target.name, len(queue), MAX_SENDS_PER_RUN)
        queue = queue[:MAX_SENDS_PER_RUN]

    for i, article in enumerate(queue):
        if dry_run:
            print(f"[{target.name}] {sinks.preview(article, target)}\n---")
        else:
            try:
                sinks.send(article, target, client)
            except PermanentSendError as exc:
                log.error("target %s: permanent failure on %s (%s); skipping article",
                          target.name, article.url, exc)
                failed.append(target.name)
                state[target.name].append(article.id)        # не блокуємо чергу назавжди
            except Exception as exc:
                log.warning("target %s: transient failure on %s (%s); rest next run",
                            target.name, article.url, exc)
                failed.append(target.name)
                break
            else:
                state[target.name].append(article.id)
        if i < len(queue) - 1:
            sleep(SPECS[target.type].delay)

    if not dry_run:
        save_state(state_path, state)                        # після кожної цілі

return sent_by_target, failed          # dict[str, int] і список імен проблемних цілей
```

Статті фетчаться один раз і переиспользуються всіма цілями.

`main()` виходить із кодом `1`, якщо `failed` непорожній. Інакше видалений Discord-webhook означає мертву ціль при зеленому CI назавжди.

`MAX_SENDS_PER_RUN = 20`. Без капу розширення фільтра (`tiers: [1]` → `[1, 2]`, або видалений `exclude_tags`) робить сотню статей «новими» за один запуск — 6+ хвилин відправки плюс flood-wait'и. Решта приходить наступного запуску за 12 годин, що і є бажаною поведінкою.

## 8. Ізоляція помилок

Чотири рівні:

1. **Фід упав** — `collect_articles` уже це ловить, решта фідів працює. Без змін.
2. **Малформований конфіг** — `load_targets` кидає до фетчу фідів. Не шлемо нічого; це друкарська помилка, яку виправляють у репо.
3. **Ціль без секрету** — пропускається з `ERROR`, решта цілей працює, вихід із кодом 1 (§3.1).
4. **Ціль упала на конкретній статті** — і це найважливіше розрізнення в усьому дизайні:

| помилка | приклад | реакція |
|---|---|---|
| **Постійна** — не-429 4xx | видалений Discord-webhook (404), Slack `invalid_payload`, Telegram 400 `can't parse entities` | `ERROR`, стаття **позначається як надіслана**, йдемо до наступної, вихід із кодом 1 |
| **Транзієнтна** — 5xx, таймаут, мережа, вичерпані ретраї 429 | сервіс лежить, раннер утратив мережу | `WARNING`, `break` по цій цілі, решта наступного запуску |

Без цього розрізнення `break` на постійній помилці робить **poison pill**: одна невідправна стаття стоїть на початку черги кожного наступного запуску, ціль не доставляє нічого назавжди, а статті за нею випадають із RSS-вікна й губляться остаточно. Найімовірніший тригер — перестворений Discord-канал, після якого webhook віддає 404 на кожен запит.

`save_state` викликається після кожної цілі, а не раз наприкінці. Раз наприкінці рятує від *винятку* в третій цілі, але не від смерті процесу (евікшн раннера, таймаут джоби, скасування) — а нова схема множить тривалість запуску на кількість цілей, тобто множить і експозицію. Ціна смерті процесу при збереженні наприкінці — повторна доставка всього, що вже пішло цього запуску.

## 9. CLI та оточення

- Новий аргумент `--targets` (дефолт `targets.yaml`).
- `--dry-run` друкує повідомлення з префіксом `[імʼя-цілі]`, не шле нічого й не пише стан. **Seed-гілка в dry-run пропускається:** інакше на чистому checkout (де `state.json` відсутній) кожна ціль пішла б у seed і dry-run не надрукував би нічого — саме тоді, коли людина перевіряє свій новий `targets.yaml`.
- `--dry-run` валідує конфіг повністю: `load_targets` викликається, `send` — ні.
- `--tz` лишається дефолтом для цілей без власного `tz`.
- `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` більше не читаються в `main` — вони приходять через `${...}` у `targets.yaml`.
- `.github/workflows/aggregate.yml`: у `env` додаються всі змінні, на які посилається `targets.yaml`.

## 10. Тестування

Файли: `test_sinks.py` (новий, замінює `test_format.py` і `test_telegram.py`), решта — розширення наявних.

`test_sinks.py`:
- один `@pytest.mark.parametrize` по `SPECS`: URL, ключ payload і маркер жирного для кожного типу;
- Telegram-рендер посимвольно збігається з нинішнім виводом `format.py` (регресія: вивід не змінюється);
- Slack екранує `<!channel>`; Discord екранує `[текст](лінк)` у заголовку **й не чіпає URL**;
- Discord payload містить `allowed_mentions`;
- webhook payload містить усі поля `Article`, `published` — ISO або `null`;
- обрізання: довгий заголовок ріжеться, url і tag виживають;
- 429 з тілом (telegram), 429 із тілом (discord), 429 із заголовком (slack), **429 з HTML-тілом → дефолт 1.0**, `Retry-After: 86400` → клемп 60, вичерпані ретраї → `RuntimeError`, не-429 4xx → `PermanentSendError`, 5xx → звичайний виняток.

`test_config.py`: резолв `${ENV}`; нерезолвлена змінна → ціль пропущена, а не виняток; малформований конфіг (невідомий `type`, дубль `name`, відсутнє обовʼязкове поле, невідомий ключ, невалідна `tz`) → `ValueError`; повідомлення про помилку не містить значення секрету; `Target.matches` одним параметризованим тестом на 6 рядків.

`test_state.py`: кап `MAX_IDS` на ціль; активна ціль не витісняє id тихої.

`test_main.py`:
- дві цілі з різними фільтрами отримують різні набори;
- **транзієнтне падіння другої цілі не чіпає `seen` першої й не заважає третій**;
- **постійна помилка не блокує чергу**: наступна стаття все одно йде, ціль у `failed`;
- нова ціль seed-иться без відправок;
- статті фетчаться один раз;
- `MAX_SENDS_PER_RUN` ріже чергу, решта лишається невідправленою;
- **нерезолвлена змінна в одній цілі не зменшує відправок з інших** (гарантія §3.1 — перевіряти саме кількість відправлених, а не факт винятку);
- `--dry-run` валідує конфіг і друкує з префіксом цілі при відсутньому `state.json`.

Файли `test_format.py` і `test_telegram.py` видаляються.

## 11. Документація

README отримує секцію «Targets»: формат `targets.yaml`, чотири типи, як дістати webhook-URL для Discord і Slack, як працюють фільтри. Плюс три застереження:
- webhook-URL — це секрет;
- дві цілі з однаковим URL і різними іменами доставлять усе двічі, і стан виглядатиме здоровим;
- відкат до однотаргетного коду вимагає видалити `state.json`.

## 12. Свідомо поза скоупом

- Паралельна відправка. Батч на 14 фідів двічі на добу відправляється послідовно за прийнятний час.
- Ретраї між запусками поза обробкою 429.
- Per-target розклад.
- Шаблони payload у YAML.
- HTTP-сервіс із REST API поверх агрегатора — окремий спек, якщо колись знадобиться.
